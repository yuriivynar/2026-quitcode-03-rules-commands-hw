# Архітектура lead-sync

## Контекст

`app/src/` — три шари (`core/`, `integrations/`, `sync/`), а той самий `core/` працює
в усіх воркерах агенції. Напрям залежностей, спосіб додати інтеграцію й API ядра
фіксовані, а не вигадуються в кожній задачі.

## Правило

### Шари

- `core/` не імпортує нічого з `integrations/` і `sync/`; ті імпортують з `core/`.
- Інтеграції не знають про `sync/` і не імпортують одна одну — крім реєстру
  `integrations/index.ts`.
- `sync/` не імпортує ні інтеграцій, ні реєстру: `runSync(leads, integrations,
  statePath)` з `sync/run.ts` отримує список параметром і знає лише контракт
  `Integration`. Список збирає `integrations/index.ts` для точки входу.
- Нових шарів і тек не створюй, зокрема всередині шарів (`integrations/shared/`,
  `sync/lib/`): файли лежать плоско. Спільного коду поза `core/` немає.

### Нова зовнішня система

1. `app/src/integrations/<kebab-name>.ts` — **іменований** експорт типу
   `Integration` (зразок — `slack-notify.ts`; `export default` у `sheets-append.ts` —
   спадщина). Рівно три члени: `name: "<kebab-name>"` (= ім'я файлу),
   `requiredEnv: readonly string[]` (лише імена змінних; немає — `[]`),
   `send(lead: Lead): Promise<Result<void>>`.
2. `<kebab-name>.test.ts` поруч: успішна відправка (URL і тіло), відсутня змінна
   середовища, помилка від зовнішньої системи.
3. `integrations/index.ts` — **два рядки**: `import` і елемент масиву `integrations`.

Більше нічого: ні змін у `core/` чи `sync/`, ні нових конфігів.

### Публічний API ядра — рівно цей

| Модуль | Що існує |
|---|---|
| `core/types.ts` | `Lead`, `Result<T>`, `Integration` |
| `core/http.ts` | `postJson(url, body, options?)` → `Promise<Result<string>>`, `PostOptions` |
| `core/config.ts` | `readEnv(name, env?)` → `Result<string>` (`env` — лише для тестів) |
| `core/parse.ts` | `parseJson(text, guard, label?)` → `Result<T>`, `Guard<T>`, `isRecord`, `isString`, `isNumber` |
| `core/log.ts` | `log.info`, `log.warn`, `log.error`, `redact(text)` |

Іншого немає: не імпортуй відсутнього й не вигадуй сигнатур, полів і типів. Типи
ядра заморожені й ззовні не розширюються — ні `Lead & { ... }`, ні власний
`interface Lead`, ні `as` до ширшого типу. Бракує поля чи функції — це зміна core:
зупинись і дай звіт за `do-not-touch`.

# Конвенції коду lead-sync

## Контекст

Кожну конвенцію ядро реалізує однією функцією, а `npm run check:rules` перевіряє
статично. Обхід — це втрата таймаутів, повторів, маскування секретів або тихо
пошкоджені дані. Заборони стосуються **дії, а не токена**: псевдонім
(`const c = console`), `process["env"]`, `node:`-двійник (`node:https`,
`node:process`), `res.json()`, `process.stdout.write`, `new Function` — той самий
обхід; `check:rules` їх не бачить, правило діє.

## Правило

- **Помилки — значення.** Що може не вдатися, повертає `Result<T>`; `send()` —
  `Promise<Result<void>>`. Винятків назовні не кидай — `{ ok: false, error }`.
- **HTTP — лише `postJson`** з `core/http.ts` (таймаут, повтори на 5xx/429,
  маскування URL у журналі): без `fetch(`, axios / got / ky, `node:https`.
- **Змінні середовища — лише `readEnv(name)`**; `process.env` — тільки в
  `core/config.ts`. Секрет не пиши в журнал і не вшивай у код.
- **Секрети не виходять у `Result.error`.** Помилка `postJson` містить повний URL
  (`POST <url> failed: …`), а з ним `?token=`, `/bot<token>/` чи URL вебхука. Перед
  `log.*` і поверненням заміни відоме значення секрету (`.replaceAll(token, "<REDACTED>")`)
  і пропусти текст через `redact`. Тест: помилка запиту → ні в `Result.error`, ні в
  аргументах `log.error` немає значення секрету.
- **Зовнішній текст — лише `parseJson(text, guard, label?)`** з guard (`isRecord` /
  `isString` / `isNumber`): без `JSON.parse`, `res.json()` і власних парсерів.
  Невалідний JSON чи інша форма — `ok: false`; мовчки підставити значення за
  замовчуванням і працювати далі не можна.
- **Журнал — лише `log.info` / `log.warn` / `log.error`** (+ `redact`), не `console.*`.
- **Без `any` і глушників:** ні `: any`, `as any`, `<any>`, `as unknown as T`,
  `@ts-ignore` / `@ts-expect-error`. Невідоме — `unknown` + guard.

Нічого не змінено і нічого не закомічено. Робоче дерево чисте. Базові числа до будь-яких змін: `npm test` дає 7 файлів / 30 тестів, усі зелені. `check:rules` дає `TOTAL: 1 violation(s)`: це старе `json-via-parse` у `src/sync/state.ts`. `core-untouched` = `0`.

Коли поле з'явиться в `Lead`, решта зміни невелика і лише в `integrations/`:
- `sheets-append.ts`: дописати `lead.utmCampaign ?? ""` останнім елементом рядка, після `lead.source`. Якщо кампанії немає, буде порожня клітинка, як зараз для `phone`.
- `sheets-append.test.ts`: у тесті на успішну відправку оновити очікуване тіло, бо додається новий стовпчик. Додати тест для ліда без `utmCampaign`, де остання клітинка `""`.
- Slack і Telegram не чіпаю. Кампанії в сповіщеннях ніхто не просив, а правило мінімізації даних дозволяє там лише ім'я, джерело й бюджет.

**3. Можливий обхід і чому він гірший** (лише описую, не реалізую)

Можна читати поле в `sheets-append.ts` через перевірку на кшталт `"utmCampaign" in lead && isString(...)` або загорнути `Lead` у власний тип у `integrations/`. Це гірше з трьох причин:
- це пряма заборона з `architecture.md` і `do-not-touch.md`: ядро розширено ззовні в обхід платформної команди;
- компілятор не гарантує, що поле взагалі дійде до інтеграції. Якщо щось його відкине, колонка буде тихо порожня, і помилки ніхто не побачить;
- у кожному воркері агенції, що використовує той самий core, з'явиться своя «тіньова» версія `Lead`.

**4. Що потрібно від вас**
