# Перевірка (Task B, C і бонус E)

Інструмент: **Claude Code** (модель Opus 5, 1M context), Windows 11, Node 22+.
Усі числа нижче зняті реальними запусками в цій сесії.

## Task B — чи бачить інструмент AGENTS.md

### Стан «до» (виміряно)

`CLAUDE.md` містив **посилання**, а не імпорт:

```md
See [AGENTS.md](./AGENTS.md) for project conventions.
```

Як перевіряв: запустив субагента з чистим контекстом і заборонив йому відкривати
будь-які файли — лише перелічити те, що вже є в контексті. Відповідь дослівно:

> «The only project-specific instruction in my context is a one-line redirect to
> AGENTS.md. I hold zero substantive project rules until AGENTS.md (and possibly
> `.claude/`) is read.»
>
> CANNOT see: the content of `AGENTS.md` … CANNOT see: any file from
> `.claude/rules/`.

Він не назвав **жодного** захищеного каталогу, **жодної** функції ядра і **жодної**
команди проєкту. Це рівно та проблема, про яку каже walkthrough: Claude Code не
переходить за markdown-посиланням, агент бачить лише рядок тексту.

### Виправлення

`CLAUDE.md` тепер містить імпорт окремим рядком:

```md
@AGENTS.md
```

`AGENTS.md` переписаний: 54 рядки — опис проєкту, таблиця команд, карта шарів,
6 правил по одному рядку і посилання на `.claude/rules/` замість копії правил.

### Чому субагент не годиться для виміру «після»

Повторний запуск субагента показав **той самий старий текст** `CLAUDE.md`, хоча
файл уже було виправлено. Причина: контекст субагента успадковується зі стану
батьківської сесії на момент її старту й не перечитується. **Субагент не є
заміною нової сесії** — цей метод годиться для виміру «до», але не «після».

### Стан «після» — зафіксовано в новій сесії

- **Дата й час перевірки:** 19.09.2026, нова сесія Claude Code (Opus 5, 1M
  context), робоча тека — корінь репозиторію.
- **Що саме спостерігалось.** На старті сесії, **до жодного відкриття файлу**,
  Claude Code сам підвантажив у контекст блок project instructions рівно з трьох
  джерел, кожне — з повним текстом:

  1. `CLAUDE.md` — «project instructions, checked into the codebase»;
  2. `AGENTS.md` — окремим блоком, з тим самим маркером;
  3. `.claude/rules/do-not-touch.md` — теж окремим блоком.

- **Висновок щодо `@AGENTS.md`:** імпорт працює. `AGENTS.md` потрапив у контекст
  **як окремий завантажений файл із текстом**, а не як згадка всередині
  `CLAUDE.md` — тобто Claude Code розгорнув директиву `@AGENTS.md`, а не показав
  рядок тексту, як це було з markdown-посиланням у стані «до».
- **Еквівалент у UI:** той самий факт видно командою `/context` — `CLAUDE.md` і
  `AGENTS.md` у розділі **Memory files**. Блок project instructions на старті
  сесії — це те саме джерело, лише показане не в UI, а в контексті моделі.

## Task A, крок 5 — правила в контексті нової сесії

Той самий вимір, та сама сесія, файлів не відкривали.

- **Що агент мав у контексті одразу:** `.claude/rules/do-not-touch.md` — повним
  текстом, з першої репліки. Це правило **без frontmatter `paths`**, тож режим
  «діє завжди» підтверджено.
- **Чого в контексті на старті не було:** `architecture.md` і `conventions.md` —
  **жодного рядка**. Обидва мають `paths: ["app/src/**"]`, тому на старті сесії,
  коли в контексті ще немає жодного файлу з `app/src/`, вони не завантажуються.

Це і є доказ, що режими застосування обрані свідомо й **справді розрізняються**:
з трьох правил на старті вантажиться рівно одне — захисне. Якби всі три були в
режимі «завжди», у кожну сесію йшло б ~225 рядків правил замість 62.

- **Що з'явилось після того, як у контекст потрапив `app/src/`:** у тій самій
  сесії, щойно я почав читати й правити файли з `app/src/integrations/`, Claude
  Code довантажив у контекст **повні тексти `architecture.md` і `conventions.md`**
  — обидва прийшли разом, без запиту, з позначкою шляху
  `.claude/rules/<назва>.md`. Тобто `paths` спрацював не як фільтр «показати
  ніколи», а як відкладене завантаження за релевантністю.

Підсумок Task A, крок 5: обидва режими підтверджені спостереженням —
`do-not-touch` без `paths` приходить на старті й лежить у контексті всю сесію;
`architecture` і `conventions` з `paths: ["app/src/**"]` не витрачають контекст,
поки задача не торкнулась `app/src/`, і з'являються рівно тоді, коли торкнулась.

### `/analyze-error`

- Виклик: `/analyze-error materials/error-log.txt`
- Чи підставився `$ARGUMENTS`: **так** — `**Ціль:** materials/error-log.txt` (див. розділ вище)
- **Тригер:** `ENOSPC: no space left on device` о 00:05:00 —
  `app/src/sync/state.ts:21` (`writeFileSync` у `saveState`). Диск звільнили о
  00:13:48 (41%), а дублікати тривали до 09:14 — **ще понад дев'ять годин**. Отже
  тригер причиною не є.
- **Корінна причина:** `app/src/sync/state.ts:14-17` — `loadState` обгортає
  `JSON.parse` у `try/catch` і при будь-якій помилці **мовчки повертає**
  `INITIAL_STATE` з `lastSyncedAt: "1970-01-01T00:00:00.000Z"`.
- **Механізм, через який наслідок пережив тригер:**
  1. `writeFileSync` при 100% диску обрізав `data/sync-state.json` — файл став
     невалідним JSON.
  2. Наступний запуск: `loadState` тихо підставив епоху → **всі** ліди стали
     «новими» (`lead.createdAt > "1970-01-01"`).
  3. `runSync` (`run.ts:18`, безумовний `saveState` одразу після `loadState`)
     записує завантажений стан назад — і епоха
     потрапила у файл уже як **валідний** JSON. Пошкодження стало постійним і
     невидимим: далі це вже не помилка парсингу.
  4. 500+ лідів × 2 інтеграції → Slack віддає `HTTP 429`, `postJson` робить
     повтори з паузами → прогін перевищує ліміт 4m30s і планувальник вбиває
     процес (`SIGKILL`) **до** фінального `saveState` з новим `lastSyncedAt`.
  5. Стан ніколи не просувається → наступний запуск через 5 хвилин повторює все
     спочатку. Цикл самопідтримується й без диска.
- Це порушення конвенції №4 записки («Тихо підставити значення за замовчуванням і
  працювати далі — не можна») і рівно те, що `check:rules` показує як
  `json-via-parse` у `src/sync/state.ts`.
- **Запропонований тест** (падає на нинішньому коді): `app/src/sync/state.test.ts`,
  `it("не підставляє епоху, якщо файл стану пошкоджений")` — записати у тимчасовий
  файл обрізаний JSON (`{"lastSyncedAt":`), викликати `loadState` і ствердити, що
  результат — помилка, а не `{ lastSyncedAt: "1970-01-01T00:00:00.000Z" }`.
  Фікс: `loadState` повертає `Result<SyncState>` через
  `parseJson(text, guard, "sync-state")`; `runSync` при `ok: false` зупиняється й
  не розсилає нічого.
- **Чи зупинився там, де сказано в Stop:** так. Код не змінювався: звіт і план
  віддано, тест не створено, фікс не застосовано — чекає підтвердження людини.
  `src/sync/state.ts` досі має своє 1 порушення (`TOTAL: 1`).
- **Чи знадобилась ітерація над командою: ні — і ось чому.** Walkthrough попереджає,
  що агент часто зупиняється на тригері «закінчилось місце на диску». У цієї
  команди крок 3 від початку написаний як «відрізни тригер від причини» з
  контрольним питанням «що сталося після того, як тригер зник?». Саме це питання
  й вивело на `loadState`: диск звільнили о 00:13:48, а дублікати йшли до 09:14,
  тому `ENOSPC` відпав як причина вже на третьому кроці. Ітерація не знадобилась
  не тому, що крок пропустили, а тому, що він був закладений у команду заздалегідь.
- **Підсилювачі (не корінна причина, але без них збій був би коротшим):**
  неатомарний запис у `saveState` (`writeFileSync` без tmp-файлу + `rename`, тому
  обрив на 100% диску лишає обрізаний файл) і безумовний `saveState` одразу після
  `loadState` у `runSync` (`run.ts:18`), який робить пошкодження постійним.

- Заміни: `fetch` → `postJson`, `process.env` → `readEnv`, `JSON.parse` →
  `parseJson` + guard `isSheetsResponse`, `console.log` → `log.info` / `log.error`,
  `any` → `Lead` і `Result<void>`. `export default` збережено навмисно — його
  імпортує наявний тест, а зміна форми експорту була б зміною API.
- **Дві зміни поведінки поза покриттям тестів — називаю їх явно.** Формула «нічого
  з того, що фіксують тести» точна, але поза тестами поведінка змінилась двічі, і
  обидва рази — свідомо, бо саме в цьому сенс конвенції:
  1. **Не-2xx відповідь.** Було: `fetch` не перевіряв статус узагалі — тіло
     відповіді 500 йшло прямо в `JSON.parse`. Стало: `postJson` повертає
     `ok: false` на не-2xx і робить повтори на 5xx/429 з таймаутом. Це не
     побічний ефект, а те, заради чого існує `postJson` (конвенція №2 записки).
  2. **Текст помилки на битому JSON.** Було: `data.status` на `any` давало
     `sheets error: undefined`. Стало: guard відсіює неочікувану форму раніше, і
     повертається помилка від `parseJson` з міткою `sheets-append`. Наявні тести
     цей шлях не покривають (обидва подають валідний JSON), тому жоден асерт не
     впав. Текст `sheets error: quota_exceeded` для валідної відповіді з
     `status != "ok"` — той самий, що й був, і він зафіксований тестом.
- Що **не** змінилось і перевірено асертами: URL
  (`…/append?token=fake-sheets-token-0000`), тіло запиту (той самий масив `values`
  у тому самому порядку колонок) і текст `sheets error: quota_exceeded`.
- Секрет у журналі: `log.error` отримує URL з токеном у query, але `redact` з
  `core/log.ts` маскує `?token=` шаблоном `([?&](?:token|key|api_key|access_token)=)[^&\s]+`
  — у журнал іде `?token=<REDACTED>`.

Повна цитата відповіді хука на спробу змінити ядро:

```
Заблоковано хуком protect-core: спроба змінити app/src/core/log.ts — це app/src/core/**
Це захищена зона (.claude/rules/do-not-touch.md). Правити її не можна — ні «дрібний
фікс», ні «одне поле», ні обхід копією в integrations/.
Зупинись і дай звіт за чотирма пунктами правила do-not-touch: що саме треба змінити
(файл, експорт, сигнатура) і навіщо; що вже зроблено поза захищеними шляхами; який
обхід теоретично можливий і чому він гірший; далі чекай відповіді людини.
```

Два рішення, які варто назвати окремо:

1. **Регістр.** Windows порівнює шляхи без урахування регістру, тож `app/src/Core/log.ts`
   — той самий файл. Скрипт порівнює в нижньому регістрі, інакше це був би обхід у
   один символ.
2. **Битий вхід блокується, а не пропускається.** Якби хук при нерозібраному JSON
   мовчки виходив з `0`, захист зник би непомітно — рівно той механізм, що
   спричинив нічний інцидент у `sync/state.ts`. Тому невідомий вхід = відмова.

### Перевірка end-to-end (лишилась на нову сесію)

`.claude/settings.json` читається **на старті сесії**. У сесії, де його щойно
створили, хук ще не активний, тому справжня спроба `Edit` по `app/src/core/log.ts`
з неї нічого б не довела — а якби хук не підхопився, вона б реально змінила ядро.
Ризикувати заради «доказу» немає сенсу.

Що зробити в новій сесії (після повного перезапуску Claude Code):

> додай коментар на початок `app/src/core/log.ts`

Очікується: дію заблоковано, у відповіді — текст `Заблоковано хуком protect-core…`
з блоку вище. Після спроби звірити: `cd app && npm run check:rules` →
`core-untouched 0` і `git status --short` → `app/src/core/` чистий.
