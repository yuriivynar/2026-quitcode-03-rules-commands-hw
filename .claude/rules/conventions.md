# Конвенції коду lead-sync

## Контекст

Кожну конвенцію нижче ядро вже реалізує однією функцією, а `npm run check:rules`
перевіряє статично. Обхід конвенції — це не «інший стиль», а втрата таймаутів,
повторів, маскування секретів або тихо пошкоджені дані.

Заборони нижче стосуються **дії, а не токена**. Псевдонім (`const c = console`),
рядковий ключ (`process["env"]`), `node:`-двійник (`node:https`,
`import { env } from "node:process"`), `res.json()`, `process.stdout.write`,
`new Function` — це той самий обхід, а не виняток. `check:rules` їх не бачить;
правило діє однаково.

## Правило

- **Помилки — це значення.** Функція, що може не вдатися, повертає `Result<T>` з
  `core/types.ts`; `send()` інтеграції завжди повертає `Promise<Result<void>>`. Не
  кидай винятків назовні — повертай `{ ok: false, error }`.
- **HTTP — лише `postJson(url, body, options?)`** з `core/http.ts`. Не використовуй
  `fetch(` напряму, не бери його через псевдонім, не заміняй на `node:https` і не
  додавай axios / got / ky: у `postJson` є таймаут, повтори на 5xx/429 і маскування
  URL у журналі.
- **Змінні середовища — лише `readEnv(name)`** з `core/config.ts`. Не читай
  `process.env` поза `core/config.ts` — ні напряму, ні через `node:process`.
  Значення секрету не пиши в журнал і не вшивай у код — навіть «тимчасово».
- **Зовнішній текст — лише `parseJson(text, guard, label?)`** з `core/parse.ts`
  разом із guard (`isRecord` / `isString` / `isNumber`). Ні `JSON.parse`, ні
  `res.json()`, ні власний парсер: без guard форма даних не перевірена. Невалідний
  JSON або неочікувана форма — це `Result` з `ok: false`; мовчки підставити
  значення за замовчуванням і працювати далі не можна.
- **Журнал — лише `log.info` / `log.warn` / `log.error`** (+ `redact`) з
  `core/log.ts`. Не `console.*` і не `process.stdout.write`.
- **Без `any` і без глушників типів.** Ні `: any`, ні `as any`, ні `<any>`, ні
  `as unknown as T`, ні `@ts-ignore` / `@ts-expect-error`. Для невідомих даних —
  `unknown` плюс guard.
- **Без нових залежностей.** Жодного нового пакета в `app/package.json` — ні в
  `dependencies`, ні в `devDependencies` (`check:rules` бачить лише перші).
  У **production-файлах** (`app/src/**`, крім `*.test.ts`) імпортувати можна лише
  відносні шляхи й `node:*`. У тестах до цього додається `vitest` — він уже в
  `devDependencies`, і без нього тесту не існує; будь-який **інший** зовнішній
  пакет у тестах — те саме порушення, що й у production. У `app/src/` лише `.ts`:
  `.js` / `.mjs` не бачать ні typecheck, ні перевірка. Потрібна бібліотека —
  спершу питання в PR, а не `npm install`.
- **Мінімізація даних.** У сповіщення (Slack, месенджери) перелічуй поля поіменно
  — лише ім'я, джерело й бюджет; не передавай `lead` цілим об'єктом і не збирай
  імена полів із рядків. `lead.email` і `lead.phone` туди не потрапляють ніколи —
  повні дані йдуть тільки в системи обліку (`sheets-append.ts`, CRM).
- **Імена.** Файли — kebab-case; поле `name` інтеграції збігається з іменем файлу.
- **Тести.** Vitest, `*.test.ts` поруч із модулем, реальної мережі немає:
  `fetch` підміняється через `vi.stubGlobal("fetch", ...)`, змінні — через
  `vi.stubEnv`. `check:rules` тести не сканує, тому тут дивись очима: заборони на
  `any`, глушники типів, реальну мережу, справжні секрети й `console.*` діють і в
  тестах. Єдиний виняток — `JSON.parse` над **власною фікстурою** в асерті
  (`JSON.parse(String(init?.body))`): це розбір рядка, який щойно склав сам тест,
  а не довіра зовнішнім даним. Так зроблено в наявних `slack-notify.test.ts` і
  `sheets-append.test.ts` — це норма проєкту, а не спадщина.
- **Наявні тести не слабшають.** Асерти й фікстури не видаляй, не переводь у
  `it.skip` і не заміняй слабшими (`toEqual` → `toMatchObject` / `toContain`).
  Змінюй асерт лише тоді, коли задача прямо описує нову поведінку, — і перелічи
  кожен змінений асерт у підсумку.
- **Спадковий код** (`app/src/integrations/sheets-append.ts`, `app/src/sync/state.ts`)
  переписується окремою задачею і без зміни поведінки: URL, тіло запиту й тексти
  помилок лишаються тими самими.

## Як перевірити

**Числа звіряй зі станом до своїх змін, а не з константою в цьому файлі.**
Перший крок будь-якої задачі — зняти `check:rules` і `npm test` до правок: числа
в таблиці застарівають щоразу, коли хтось переписує черговий спадковий модуль.

| | `TOTAL` | ненульові в `by rule` | тести |
|---|---|---|---|
| стартова лінія репо (до Task C) | `8` | `http-via-core 1`, `env-via-config 1`, `json-via-parse 2`, `log-via-logger 2`, `no-any 2` | 6 файлів / 18 |
| поточний стан | `1` | `json-via-parse 1` (`src/sync/state.ts`) | 7 файлів / 23 |

- `cd app && npm run check:rules` → `TOTAL` **не більший, ніж був до твоїх змін**;
  у секції `by file` немає нових рядків для файлів, які ти змінював;
  `core-untouched` = `0`. `*.test.ts` перевірка не сканує — там дивись очима.
- `cd app && npm test && npm run typecheck` → зелено; тестів **не менше, ніж було
  до змін**.
- Мінімізація даних (git bash):
  `grep -rnE "lead\.(email|phone)|\blead\b\s*[,}]" app/src/integrations/ --include="*.ts" | grep -v "\.test\.ts:"`
  → допустимий лише `sheets-append.ts` (система обліку); модуль-сповіщення в цьому
  виводі — порушення.
- Нових залежностей немає: `git diff HEAD -- app/package.json app/package-lock.json`
  → порожньо, і `no-new-deps` у `check:rules` = `0`.
